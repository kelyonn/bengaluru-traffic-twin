# Bengaluru Traffic Twin — MQTT Data Schema & Log

This documents every message the traffic twin produces, in the per-signal-node
MQTT architecture. The log is generated by `build_mqtt_log.py` from the SUMO
simulation outputs. **No broker is contacted yet** — these are the exact
messages that will be published once a broker is wired in.

---

## 1. Where the data comes from

| Layer | Source | Real? |
|-------|--------|-------|
| Signal nodes (positions + OSM IDs) | OpenStreetMap `highway=traffic_signals` | **Real** |
| Areas (names + locations) | OpenStreetMap `place=suburb` | **Real** |
| Road network & which roads feed each signal | OpenStreetMap → SUMO | **Real** |
| Per-approach speed / density / counts | SUMO simulation (demand shaped by real residential→IT commute patterns + rush-hour curve) | **Simulated** |

**Every signal is a real OSM traffic signal**, carried with its OSM node id
(e.g. `n62053503`). Each is matched to the nearest SUMO roads (within 45 m);
those roads are its **approaches** — one virtual detector per approach, as if a
camera/radar at the signal counted each incoming direction. The approach's
simulated speed/density becomes the detection.

- **1,377 signal nodes** (real OSM) across **95 areas** (real OSM suburbs)
- 2 signals sit outside the drivable network → registered (status/identity) but emit no detections
- Simulation window: **2026-06-15 07:00 – 10:00 IST** (morning peak)
- Aggregation interval: **300 s (5 min)**

## 2. Topic hierarchy

```
traffic/{city}/{area}/{signal_id}/data        detection payloads
traffic/{city}/{area}/{signal_id}/heartbeat   liveness pings
traffic/{city}/{area}/{signal_id}/alert       congestion / incident (high priority)
traffic/{city}/{area}/{signal_id}/frames      evidentiary frame references
management/{city}/{area}/{signal_id}/status   node → server status
management/{city}/{area}/{signal_id}/command  server → node commands (inbound; not generated here)
```

- `city` = `bengaluru`
- `area` = e.g. `koramangala`, `whitefield`, `cbd_mg_road` (see `areas.json`)
- `signal_id` = `signal_001` … (numbered per area)

**Subscription examples**
```
City server   →  traffic/bengaluru/#
Area server   →  traffic/bengaluru/koramangala/#
Single node   →  traffic/bengaluru/koramangala/signal_007/#
All alerts    →  traffic/bengaluru/+/+/alert
```

## 3. Message types

### 3.1 `data` — detection payload  (QoS 1, retain false)
Emitted per signal per interval. The core traffic measurement.

```json
{
  "signal_id": "signal_007",
  "area": "koramangala",
  "city": "bengaluru",
  "osm_node_id": "n62053503",
  "interval_start": "2026-06-15T08:15:00+05:30",
  "interval_secs": 300,
  "total_vehicle_count": 184,
  "overall_congestion": "heavy",
  "detectors": [
    {
      "approach": "N",
      "heading": "N",
      "vehicle_count": 96,
      "mean_speed_kmh": 12.4,
      "density_veh_km": 38.2,
      "occupancy_pct": 38.2,
      "congestion": "heavy"
    }
  ]
}
```

| Field | Unit | Meaning |
|-------|------|---------|
| `interval_start` | ISO 8601 | start of the 5-min window |
| `total_vehicle_count` | vehicles | sum over approaches (estimate: density × approach length) |
| `overall_congestion` | enum | worst approach level (see below) |
| `detectors[]` | — | one entry per approach with traffic data |
| `mean_speed_kmh` | km/h | simulated mean speed on that approach |
| `density_veh_km` | veh/km | vehicles per km of road |
| `occupancy_pct` | % | detector occupancy proxy |

**Congestion levels** (relative speed = mean ÷ free-flow):
`free` ≥0.70 · `moderate` 0.40–0.70 · `heavy` 0.25–0.40 · `jam` <0.25

### 3.2 `heartbeat` — liveness  (QoS 0, retain false)
```json
{ "signal_id":"signal_007","status":"online","uptime_s":4500,
  "fw_version":"twin-1.0.0","detectors_ok":3,"detectors_total":4 }
```
Cadence here = 300 s (matched to data). Real nodes typically beat every 30–60 s
(`HEARTBEAT_SECS` in the builder).

### 3.3 `alert` — congestion / incident  (QoS 2, retain false)
Emitted only when an approach drops below the jam threshold (rel <0.25).
```json
{ "alert_id":"alt_000123","signal_id":"signal_007","area":"koramangala",
  "type":"congestion","severity":"high","approach":"S","heading":"S",
  "measured_speed_kmh":4.4,"relative_speed":0.087,"threshold_rel":0.25,
  "ts":"2026-06-15T08:15:00+05:30" }
```
QoS 2 = exactly-once, because alerts must not be lost or duplicated.

### 3.4 `frames` — evidentiary frame reference  (QoS 1, retain false)
Paired with each alert. **References only — never raw image bytes over MQTT.**
```json
{ "frame_id":"4eed7274b93246da","alert_id":"alt_000123",
  "signal_id":"signal_007","area":"koramangala",
  "uri":"s3://traffic-evidence/bengaluru/koramangala/signal_007/4eed7274b93246da.jpg",
  "captured_ts":"2026-06-15T08:15:00+05:30","resolution":"1920x1080",
  "sha1":"4eed7274b93246da",
  "note":"reference only — raw bytes transferred out-of-band" }
```

### 3.5 `status` — node → server  (QoS 1, **retain true**)
One per signal at boot, retained so a late subscriber immediately learns each
node's identity, location, and health.
```json
{ "signal_id":"signal_007","area":"koramangala","city":"bengaluru",
  "lat":12.9352,"lon":77.6245,"n_approaches":4,"fw_version":"twin-1.0.0",
  "health":"online","detector_mode":"auto","config_version":1,
  "boot_ts":"2026-06-15T07:00:00+05:30" }
```

## 4. Files in this folder

| File | Contents |
|------|----------|
| `mqtt_log.jsonl` | **Every message** in publish order. One JSON object per line: `{ts, sim_t, topic, qos, retain, payload}` |
| `by_type/data.jsonl` | Detection payloads only |
| `by_type/heartbeat.jsonl` | Heartbeats only |
| `by_type/alert.jsonl` | Alerts only |
| `by_type/frames.jsonl` | Frame references only |
| `by_type/status.jsonl` | Retained node-status messages |
| `signals.json` | Signal registry: id, area, lat/lon, approaches |
| `areas.json` | Area name → bounding box |
| `summary.json` | Counts and topic patterns |

Each `mqtt_log.jsonl` line is a ready-to-publish envelope:
```json
{"ts":"...","sim_t":4500,"topic":"traffic/bengaluru/koramangala/signal_007/data",
 "qos":1,"retain":false,"payload":{...}}
```
A publisher just needs to read each line and call
`client.publish(topic, json.dumps(payload), qos=qos, retain=retain)` —
optionally paced by `sim_t` to replay the morning peak in real time.
